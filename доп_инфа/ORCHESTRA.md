# Описание продукта: Платформа управления бизнес-процессами (Цифровой двойник бизнеса)

## 1. Концепция продукта
Платформа представляет собой систему для моделирования, управления и исполнения бизнес-процессов (BPMS). Основная цель — создать «цифровой двойник бизнеса», где процессы визуализируются в виде направленных графов, а управление задачами максимально автоматизировано с помощью ИИ и Telegram-бота. 
Платформа позволяет не только конструировать процессы, но и запускать по ним реальные проекты (экземпляры процессов), отслеживая движение ресурсов и статусы задач в реальном времени.

**Технологический стек (окончательный):**
- **Frontend:** React + Vite + TypeScript + React Flow (Canvas/WebGL графы) + Tailwind CSS + Zustand.
- **Backend:** Go (chi роутер, pgx + PostgreSQL, zap логирование).
- **Telegram-бот:** Go (telebot.v3).
- **ИИ:** HTTP-клиент к OpenAI/DeepSeek API.
- **БД:** PostgreSQL (нормализованная, миграции golang-migrate).
- Адаптивный дизайн для мобильных устройств.
**БД:** Нормализованная структура (задачи, ресурсы, связи хранятся отдельно, а не монолитным JSON) для быстрой работы SQL/графовых запросов.

## 2. Пользовательский интерфейс и UX (Граф процессов)
- **Визуальный редактор (Canvas/WebGL):** Процесс строится слева направо. 
  - **Задачи (unit-задачи):** Отрисовываются прямоугольниками с острыми углами. Содержат: название, инструкции, стоимость, эстимацию (план/факт), исполнителя, контролирующего(их можно указать при создании или изменить после).
    - **Редакция прямо на холсте:** Всю редакцию задачи можно производить прямо на холсте — вводить/изменять название и инструкцию, назначать исполнителя (выпадающий список участников команды, включая отделы и ИИ). Для остальных полей (стоимость, эстимация, контролирующий, ресурсы) у узла есть кнопка редактирования, открывающая отдельное диалоговое окно.
    - **Тип исполнителя (единое поле):** Исполнитель определяется выбором в выпадающем списке: человек (из команды), отдел или ИИ. Отдельной радиокнопки «ИИ» НЕ существует — выбор «ИИ» в списке исполнителей задаёт и способ уведомления (личка/группа/мгновенный промпт), и правила выполнения.
    - **Отображение инструкции:** Инструкция выводится прямо на узле в укороченной форме (сколько влезет). Узел можно расширить вниз, чтобы увидеть всю информацию.
  - **Ресурсы:** Отрисовываются прямоугольниками с закругленными углами. Это очередь из ресурсов запущенных проектов, которые выводятся на граф в соответствующий узел. То, что для одной задачи является выходом, для другой — вход. Ресурсы могут быть ссылками (Google Docs и др.) или внутренними текстовыми документами (Markdown), что критично для работы ИИ.
- **Стартовая точка:** Обязательная задача «Запуск проекта», которая всегда есть на холсте.
- **Финал:** Исходящие ресурсы процесса выделяются в визуальный кластер «Результат».
- **Валидация:** Система подсвечивает «оборванные» узлы (задачи без входов/выходов, ресурсы в никуда), если они не являются частью финального «Результата».
- **Интерактивность:** Возможность добавлять, удалять, перетаскивать узлы и запрашивать авто-компоновку для удобного вида (как в base_ui).
- **Авто-компоновка:** Кнопка на левой панели редактора. Запускает алгоритм layered/DAG layout, выстраивающий узлы слева направо по направлению рёбер. Полностью пересчитывает позиции всех узлов (ручные позиции не сохраняются при повторной компоновке — это умышленно), но НЕ меняет структуру графа. После авто-компоновки можно продолжать ручные правки (перетаскивание узлов).

### Группировка по исполнителю и портфель исполнителя:
- **На главном холсте** — включаемая опция «Сгруппировать по исполнителю» (переключатель на верхней панели редактора). Когда активна, задачи оборачиваются в цветные зоны-кластеры по исполнителям (с подписью имени/отдела/ИИ).
- **Отдельная панель «Портфель исполнителя»** (на вкладке «Команда» или как боковая панель) — выбранный исполнитель виден как мини-граф: только его задачи + входящие и исходящие ресурсы. Из этой панели можно перетащить отдельную задачу (или весь мини-граф) на главный холст — добавляется копия куска в процесс (как из библиотеки, но с сохранением исполнителя).
### Модель стоимости и эстимации:
- **Плановая эстимация** — число (в часах), задаётся автором при создании задачи; используется для расчёта SLA и дисциплины.
- **Фактическое время выполнения** — считается от «взял в работу» до «сдал», но только по рабочему времени (минус личное время по кнопкам «Начал/Закончил работу», минус нерабочее время отдела).
- **Среднее фактическое время** — среднее по всем выполненным экземплярам данной задачи, агрегируется автоматически. При отсутствии истории показывается «—».
- В Библиотеке процессов плановая эстимация не хранится; при переносе куска на холст она по умолчанию подставляется равной среднему фактическому времени (если оно есть).
- **Стоимость** — число, задаётся автором задачи (стоимость выполнения задачи).

## 3. Проекты (Экземпляры процессов)
- **Модель создания проекта:** Единая кнопка «Создать проект» (на вкладке «Проекты» и/или в тулбаре редактора) открывает модальное окно создания. Пользователь заполняет: название проекта и выходные ресурсы стартовой задачи «Запуск проекта» (ссылки или текст). Каждое поле ресурса = одна ссылка/текст, которая становится экземпляром ресурса со статусом «Существует, Не обработан». Проекту автоматически присваивается цвет (из палитры «тембров»), который окрашивает его ресурсы на холсте. Созданный проект сразу получает статус «Запущен», и движок начинает маршрутизацию по графу.
- **Версионирование (Snapshots):** При запуске проект фиксирует текущий слепок графа. Если граф процесса позже редактируется, изменения применяются *только к новым проектам*. Старые проекты идут по изначальному маршруту.
- **Цветовое кодирование:** Каждому проекту при создании присваивается свой цвет.
- **Отображение ресурсов проектов на холсте:** На узлах-ресурсах графа отображаются агрегированные бейджи-счетчики (фокус на необработанные ресурсы). При клике элемент увеличивается и выводится вся очередь ресурсов по каждому запущенному проекту в их цветах. Выводятся только ресурсы активных проектов.

## 4. Маршрутизация и статусы
### Статусы задач (пересчитываются автоматически):
- **Ожидание:** нет всех необходимых входящих ресурсов.
- **Готов к выполнению:** все входящие ресурсы собраны. Задача автоматически отправляется исполнителю.
- **В работе:** исполнитель взял задачу.
- **Выполнен:** исполнитель прикрепил исходящие ресурсы и сдал работу.
- **Заблокирован (Blocked):** локальная проблема при выполнении. Затрагивает только конкретную задачу, параллельные ветки проекта продолжают работу.
  - При создании блокировки исполнитель указывает комментарий/причину (через кнопку «Сообщить о проблеме»), видимую контролирующему.
  - `Blocked` снимается ВРУЧНУЮ контролирующим или менеджером (с комментарием); при снятии задача возвращается в «В работе» (или в «Готов к выполнению», если её никто не взял).
  - Нехватка ресурсов — это статус «Ожидание», а НЕ `Blocked`. `Blocked` используется только когда проблема реальная и требует вмешательства человека.

### Схема уведомлений при блокировке/разблокировке:
- При переходе задачи в `Blocked` уведомляется **контролирующий** задачи (с причиной и ресурсами).
- **Владелец/менеджер проекта** уведомляется только при эскалации (например, если контролирующий не среагировал за N времени), чтобы не засыпать его каждым блоком.
- **Последующие задачи** (ждущие выходы) отдельно не уведомляются — они остаются в `Waiting`; при фактическом разблокировании и выполнении движок пересчитает статусы и уведомит следующих исполнителей по обычной логике.
- При **разблокировке** уведомляется исполнитель (задача возвращена в работу/готовность).

> **Примечание:** Промежуточного статуса приёмки/«На проверке» не существует. Сдача задачи сразу переводит её в статус «Выполнен». Контролирующий не утверждает результат, а лишь информируется об изменениях статуса.


### Статусы проектов:
- **Запущен:** в процессе исполнения.
- **Приостановлен (Paused):** временная остановка менеджером вручную (SLA заморожен, исполнители уведомлены). Можно «Возобновить». Отличается от статуса Blocked у задач.
- **Архивирован (Archived):** окончательная принудительная остановка. Требует двухэтапного подтверждения (модальное окно с предупреждением «Все работы по проекту прекращаются»). Активные задачи при архивации не удаляются, а переходят в замороженное состояние. Проект исчезает из активных очередей ресурсов на холсте и виден под спойлером на вкладке «Проекты». «Вернуть из архива» переводит проект снова в статус «Запущен» с пересчётом статусов задач.
- **Правило паузы/архивации:** Пока проект в статусе `Paused` или `Archived`, движок НЕ переводит задачи в «Готов к выполнению» и НЕ отправляет никаких уведомлений — задачи замирают в текущих статусах. При снятии паузы (возврате в статус «Запущен») движок мгновенно пересчитывает статусы всех ожидающих задач; те, у кого входы собраны, переходят в «Готов к выполнению» и отправляются по логике уведомлений (с учётом флага «занят» и рабочего времени).
- **Завершен:** достигнут кластер «Результат».
- **Архивирован:** принудительная остановка (с обязательным подтверждением), скрывается под спойлер на вкладке Проектов с возможностью восстановления.

### Статусы ресурсов:
- Не существует, Существует (есть ссылка), Обработан, Необработан(есть задачи для которых этот ресурс входящий и они не в статусе Выполнен).

## 5. Исполнители и Telegram-интеграция
Исполнителем может быть: Человек, Команда или ИИ.
- **Авторизация:** Вход в Web-интерфейс осуществляется **исключительно через Telegram Login Widget** (без паролей), чтобы жестко связать web-аккаунт сотрудника и бота.
- **Бот как основной интерфейс работы:** 
  - *Для человека:* бот присылает уведомления в личку (проект, описание, входящие ресурсы, инструкции, ожидаемый результат). У пользователей в телеграм есть возможность вывести список задач , которые готовы к выполнению , назначеных на него или его отдел, взять задачу к выполнению, сообщить о проблеме при выполнении (происходить информирование контролирующего и задача в статусе blocked), сдать задачу , Также бот контролирует если идет задержка при выполнении задач, запоминая время выполнения задачи по каждому проекту.
  - *Для команды:* бот присылает сообщение в групповой чат отдела с inline-кнопкой «Взять в работу». Нажатие закрепляет задачу за конкретным человеком (защита от задвоения).

### Логика уведомлений (для человека):
- У человека есть флаг **«занят»**: если у него есть хотя бы одна задача в статусе «В работе», уведомления о новых готовых задачах ему **не отправляются**.
- Уведомления приходят только если человек **свободен** (нет задач «В работе») **и** «на работе» (не в личном времени).
- В командный чат уведомления присылаются согласно времени, установленному в настройках (рабочие часы отдела).

### Сдача командных задач:
- Сдать задачу (прикрепить исходящие ресурсы) может **тот, кто её взял** (зафиксированный исполнитель), либо **контролирующий** задачи.
- Если зафиксированный исполнитель не может продолжить, он может «Отказаться» — задача снова становится доступной в групповом чате для другого участника (снова с кнопкой «Взять в работу»).
- Время выполнения (для SLA) привязывается к фактическому интервалу между «взял» и «сдал» зафиксированным исполнителем.

- **Сдача и контроль качества:**
- **SLA и учет времени:** Исключены сложные календари. Исполнитель сам нажимает в боте «Начал работу» / «Закончил работу» (личное время). В личное время таймеры SLA на его задачах ставятся на паузу, бот не шлет пуши. Для командных чатов рабочее время настраивается статично.
- **Иерархия рабочего времени (личное время vs часы отдела):**
  - **Личное время человека — всегда приоритет** над статичными часами отдела.
  - Таймер SLA задачи идёт только в пересечении: рабочее время отдела (статичные часы) + личное время человека («на работе»).
  - Если человек нажал «Закончил работу» (личное время) — таймер заморожен независимо от часов отдела.
  - Если человек «на работе», но сейчас вне рабочего времени отдела — таймер тоже стоит.
  - Если у отдела часы не заданы — учитывается только личное время человека.
  - Итог: таймер SLA идёт, когда человек «на работе» И (отдел в рабочее время ИЛИ у отдела часы не заданы).
- **SLA-контроль задержки задачи:**
  1. Отсчёт SLA начинается с момента перехода задачи в статус «В работе» и идёт только по рабочему времени (минус личное время, минус пауза проекта, минус нерабочее время отдела).
  2. При превышении плановой эстимации бот отправляет первое уведомление исполнителю (в личку или групповой чат) и контролирующему — «Задача превысила плановую оценку».
  3. Далее бот напоминает не чаще раза в заданный период (например, раз в N рабочих часов), без спама. Контролирующему уходит эскалация.
  4. После сдачи формируется запись о фактическом времени (для среднего и дисциплины), эскалации прекращаются.
- **Для Контролирующего** бот информирует о возникновении проблемы при исполнении задачи.
- **Контролирующему сообщается об изменениях статуса задачи** (взята в работу, выполнена, заблокирована и т.д.). Из бота контролирующий может ознакомиться с ресурсами задачи.
- **Бот-менеджер (свободный режим общения в личном чате):** интеллектуален, может предоставить информацию по любому проекту, к которому у человека есть доступ, помочь при выполнении задачи (если просит исполнитель), похвалить при завершении, поддерживать непринуждённый диалог.
  - **Контекст:** видит доступные человеку проекты и его задачи (по правам доступа).
  - **Безопасность:** НЕ раскрывает данные проектов, к которым у человека нет доступа; при сомнении перенаправляет на контролирующего.
  - **Доступность:** свободное общение — только в личном чате с ботом (не в групповых чатах).

## 6. Искусственный интеллект (ИИ) в системе
- **ИИ-исполнитель (один):** В системе существует ОДИН ИИ-исполнитель, конфигурация которого (провайдер, API-ключ, модель) задаётся в настройках (раздел ИИ). Задаётся выбором «ИИ» в едином списке исполнителей задачи (без отдельной радиокнопки). При готовности задачи платформа собирает промпт из входящих ресурсов и инструкций и делает запрос к API.
  - **Невозможность выполнения:** Если задача не может быть выполнена этой моделью (например, неподходящий тип контента/инструкций), ИИ СООБЩАЕТ об этом контролирующему (задача при необходимости переходит в `Blocked` с пояснением).
  - **Результат генерируется отдельно для каждого исходящего ресурса** задачи (общий контекст из входящих ресурсов + специфичная инструкция конкретного ресурса). Каждый результат сохраняется как внутренний текстовый ресурс соответствующего экземпляра.
  - Задача считается «Выполнен» только когда у ВСЕХ её исходящих ресурсов есть контент/ссылка.
- **Двухуровневый профайлинг сотрудников:** 
  - *Явный:* анкета при онбординге в боте (предпочтения по тону общения).
  - *Теневой:* анализ свободных комментариев и сроков сдачи задач. 
  - Бот адаптирует стиль общения под профайл. Сотрудник может посмотреть свой профайл (команда `/my_profile`) и оспорить выводы ИИ.
- **Генерация документов (Вакансия / Инструкция):** Для каждого Исполнителя в редакторе есть кнопки для генерации документов профиля должности. Документы генерируются on-the-fly (на лету) на основе текущих задач на холсте, не версионируются и не сохраняются как статические копии.
- **Доступы и ключи (Настройки):** Вкладка "настройки" и раздел ИИ, где пользователь указывает пути/доступы для ИИ, логин/пароль при необходимости (почта, документы и т.д.), API-ключ для ИИ (deepseek, openai и т.д.) и токен Telegram-бота. Хранение секретов (API-ключи, токен бота, логины/пароли) осуществляется НА СЕРВЕРЕ в зашифрованном виде, чтобы ИИ-исполнитель мог работать автономно и чтобы токен бота не был доступен в браузере. На клиенте хранятся только безвредные настройки (например, выбранный провайдер ИИ).

## 6а. Организации (мультитенантность)
- В системе есть **организации** (компании/бизнесы). Каждая организация — изолированное пространство со своим владельцем, командой, процессами, проектами и ресурсами.
- **Пользователь может принадлежать нескольким организациям** и переключаться между ними.
- **Библиотека процессов** — общая/публичная: типовые процессы доступны ВСЕМ организациям, но при переносе на холст они попадают в приватное пространство организации.
- Все объекты (процессы, проекты, задачи, ресурсы, команда) привязаны к организации; доступ — через членство в организации + роли (Владелец/Менеджер/Исполнитель).

### Онбординг:
- Авторизация — строго через Telegram Login Widget (без паролей).
- Если у пользователя нет ни одной организации, показывается экран: «Создать организацию» (указать название) или «Ввести пригласительный код».
  - **Создание организации:** пользователь указывает название и становится её Владельцем; попадает в пустое рабочее пространство.
  - **Присоединение по коду:** владелец может сгенерировать пригласительный код; новый пользователь вводит его и присоединяется к организации (роль Исполнителя по умолчанию; роль/права назначает владелец).
- Если пользователь уже состоит в организациях — он видит переключатель организаций.

### Двухуровневая модель ролей:
- **Роль платформы (глобальная):**
  - **Разработчик (Admin платформы)** — единственный глобальный администратор: модерация библиотеки, обработка обратной связи/донатов, технические настройки, доступ ко всем организациям в технических целях. Это отдельный тип аккаунта, привязанный к разработчику, НЕ обычный член организации.
- **Роли внутри организации:**
  - **Владелец организации** — управляет своей организацией: процессы, проекты, команда, выдача прав на правку процессов, настройки организации.
  - **Менеджер/Контролирующий** — управляет проектами организации, распределяет задачи.
  - **Исполнитель** — берёт/сдаёт задачи.
- Пользователь в разных организациях может иметь РАЗНЫЕ роли.

### Видимость проектов в организации:
- **Владелец** — видит ВСЕ проекты организации.
- **Менеджер/Контролирующий** и **Исполнитель** — видят только проекты, в которых они участвуют (являются исполнителем или контролирующим хотя бы одной задачи), и их ресурсы.
- **Видимость vs Действия:** Если пользователь участвует в проекте (исполнитель/контролирующий хотя бы одной задачи), он видит ВЕСЬ граф проекта и все его ресурсы/задачи. Но ДЕЙСТВОВАТЬ (брать/сдавать/разблокировать) он может только в рамках задач, где он исполнитель или контролирующий. Права действий определяются ролью и привязкой к конкретной задаче, а не видимостью.
- «Бот-менеджер» руководствуется той же видимостью при ответах.

## 7. Вкладка "Библиотека процессов"
- **Назначение:** общий каталог типовых процессов, доступных ВСЕМ пользователям платформы, чтобы облегчить владельцам бизнеса построение процессов. Куски (типовые процессы) можно перетащить на свой холст.
- В библиотеку сохраняются куски процесса (задачи + ресурсы + инструкции, без привязки к конкретным исполнителям и эстимациям).
- **«Предложить для библиотеки»:** пользователь может предложить кусок своего проекта (по алгоритму выделения: выделить узлы → «Предложить для библиотеки» → ввести описание). Предложение попадает разработчику на рассмотрение.
- **Двухуровневая модель каталога:**
  - **Официальные типовые процессы** — добавляет только разработчик через админ-интерфейс; помечаются как «Официальные»/проверенные.
  - **Предложенные пользователями** — попадают на модерацию разработчику (в админ-вкладку «Обратная связь» / раздел «Предложения библиотеки»); решение: опубликовать, отклонить или оставить как «Черновик». Опубликованные помечаются как «Пользовательские».
- При перетаскивании шаблона на холст чужие инструкции НЕ применяются автоматически без проверки: шаблон переносится как есть (в рамках слияния ресурсов), но владелец процесса остаётся ответственным за его содержание.
- При перетаскивании куска из библиотеки на холст срабатывает обязательный шаг **«Слияния ресурсов» (Merge Resources)**, где система заставляет связать входные/выходные концы импортированного куска с уже существующими на холсте ресурсами, исключая появление разрывов в графе.

## 7а. Обратная связь, вопросы и донаты (коммуникация с разработчиком)
- Отдельная вкладка коммуникации с разработчиком, где пользователь может задать вопрос, оставить обратную связь или отправить донат.
- **Хранение — в БД платформы** (таблица `feedback`):
  - `type` — `question` | `feedback` | `donation` | `library_suggestion`.
  - `user` — отправитель (связь с пользователем Telegram).
  - `content` — текст обращения.
  - `project_snippet_json` — для `library_suggestion`: кусок графа (задачи+ресурсы+связи+описание).
  - `donation_amount` / `donation_currency` — для донатов.
  - `status` — `new` | `read` | `in_progress` | `done` | `rejected`.
  - `created_at` — время.
- **Донаты (упрощённый механизм):** реального приёма платежей ВНУТРИ платформы нет. При нажатии «Отправить донат» система показывает реквизиты/ссылку разработчика (платёжный сервис/крипто/карта), заданные в настройках. Запись `donation` фиксирует намерение (и сумму, если пользователь укажет); фактическое зачисление происходит вне платформы. Опционально — кнопка «Я отправил донат» для уведомления разработчика.
- **Интерфейс для разработчика:**
  1. Уведомления в личный Telegram разработчика при новой заявке (карточка: тип, пользователь, текст, кнопка «Открыть»).
  2. Админ-вкладка «Обратная связь» (видимая только по роли администратора): таблица заявок, фильтры по типу/статусу, просмотр кусков-предложений, отметка статуса.
  3. Экспорт в CSV/Markdown одной кнопкой.

## 8. Вкладка "Проекты"
Сводный дашборд. Выводит всю информацию по проекту, созданные ресурсы и задачи (в работе, готов к выполнению, заблокирован). 
- Возможность фильтрации проектов по конкретному процессу.
- Архивация проектов и их восстановление.

## 9. Вкладка "Команда"
- Можно указать людей (ФИО, телеграм(обязательно), должность, рейтинг) или отдел  (название, чат в телеграмм)
- для каждого участника команды или отдела 2 кнопки: "вакансия" и "инструкция" -формирует при помощи ии вакансию или должностную инструкцию исходя из задач по которым укана исполнителем 

### Добавление участника в команду:
- Владелец на вкладке «Команда» добавляет участника, указав его Telegram-username (обязательно), ФИО, должность, отдел (опционально).
- Если пользователь с таким Telegram уже есть в платформе — добавляется сразу (с ролью, которую назначит владелец).
- Если его нет — создаётся «ожидающая» запись; при первом входе человека в платформу через Telegram система автоматически связывает его с записью и добавляет в организацию (роль по умолчанию — Исполнитель).
- Связка идёт по Telegram ID/username; явного «акцепта приглашения» заранее не требуется.

### Права на правку бизнес-процесса:
- Владелец на вкладке «Команда» может дать пользователю право на правку бизнес-процесса. Без этого права пользователь имеет доступ к процессу только на чтение.

### Отдел как тип исполнителя:
- **Отдел — самостоятельный тип исполнителя** со своей карточкой (название, групповой чат в Telegram).
- У **человека** есть опциональное поле «отдел» (связь с карточкой отдела), используемое для фильтров, истории и опции «задачи, готовые к выполнению, назначенные на меня или мой отдел» в боте.
- Задача может быть назначена либо на **отдел**, либо на **человека** независимо:
  - На отдел → уведомление в групповой чат с inline-кнопкой «Взять в работу» (первый взявший фиксируется как исполнитель).
  - На человека → уведомление в личку (по логике «занят/свободен»).

### Модель рейтинга исполнителя:
- Рейтинг исполнителя — агрегированный показатель из двух компонент:
  1. **Качество ресурсов** — среднее по оценкам тех, кто использовал созданные им ресурсы (базовая оценка нейтральная, снижается при нажатии «Входящие данные были плохими»).
  2. **Дисциплина** — доля задач, сданных в срок относительно эстимации (учитывается при наличии данных).
- Рейтинг отображается в карточке исполнителя на вкладке «Команда» (числом или «тембром»-уровнем).
- При отсутствии достаточных данных рейтинг показывается как «—» (не определён), а НЕ как «0».

## 10. Вкладка "История проектов"
- Выводится всё, что происходило с проектом: кто, что и когда сделал (хронология всех событий по проекту).
- Все данные выводятся таблицей.
- Вычисляется время выполнения задачи, а также сумма и среднее значение по этому показателю.
- Есть фильтры по датам и по исполнителю.

## 11. Итерфейс
- В центре бесконечный холст (граф процессов).
- Слева меню управления графом с возможностью свернуть/развернуть.
- Справа вкладки (контекстный контент) с возможностью свернуть/развернуть или расширить/сузить.
- Все правки/редакции происходят НА холсте (на графе). Для узлов графа (задач и ресурсов) есть кнопка редактирования, открывающая отдельное диалоговое окно.
- Глобальные настройки (провайдеры ИИ, токен бота, рабочие часы) — отдельная страница, открываемая по шестерёнке (⚙).
